## Prompt and Output Standards (13:08–13:14 - 6 min)
### Cleaner test-script structure
- Remove source and workflow-step text when it adds noise; retain the actual action and expected outcome needed by the tester
- Preserve workflow-derived wording when it represents a real rule or reference; do not let the model independently decide that a workflow step is unnecessary
- Use the reviewed Excel tab as the target format, with the action and expected result organized for straightforward testing and import
- Include work steps in a dedicated field when they exist; use `N/A` for standard setup steps that do not map directly to a workflow step
- Keep comments and workflow references available for traceability rather than overwriting them during cleanup

### Prompt governance
- Store the complete, current prompt in ClickUp so Allison, Patrick, and others can update one shared version
- Run the prompt wherever appropriate, including ClickUp, without making ClickUp-specific task creation mandatory
- Require the AI to ask clarifying questions, avoid fabrication, explain uncertain spreadsheet values, and state “I don’t know” when necessary
- Require proposed changes before any prompt or workbook update; apply changes only after approval
- Use the reviewed desired output as the model’s example rather than showing the original, less desirable output

## Workflow and Test-Script Data Model (13:15–13:24 - 9 min)
### Parent workflows and identifiers
- The workflow library will contain approved workflows as parent records, with identifiers such as `WF 5.7`
- Customer workflow IDs remain stable and will be used to build Cerner tree-view URLs
- Workflow names should be normalized for consistency, while source identifiers and links remain available for traceability
- Imported fields include workflow names, work-step numbers, decision points, start/stop points, project name, medical service, encounter type, patient information, status, and source links

### Test types and dependencies
- Each Excel tab represents a scenario or test script linked to its parent workflow
- Store scripts as separate test types linked to the parent rather than deeply nested subtasks
- Subtasks are unsuitable for large volumes because they lose step-level granularity and complicate imports
- Dependencies should link workflows and scripts without collapsing the individual test steps
- Filtering and dashboards should support workflow ID, workflow name, patient, work stream, status, medical service, encounter type, and test type

## Tester-Facing Excel Design (13:24–13:30 - 6 min)
### Required tester information
- Keep the workbook focused on what the tester must execute and mark complete
- Retain patient name, MRN, BIN, account number, location, medical service, encounter type, and primary/secondary information where applicable
- Keep patient demographics high level in the script and maintain more detailed information in a master scenario sheet
- Link script scenarios one-to-one with the master patient or scenario list when practical; use lookups rather than duplicating excessive columns
- Distinguish tester-facing execution details from back-end reporting and import fields

### Workflow references
- Use explicit wording such as the actual workflow ID or workflow-step text when the tester or reviewer needs to trace an action
- Do not replace valid workflow logic with generic language merely to make the output shorter
- Use placeholders such as `RevCycle IT to confirm location` or `RevCycle IT to confirm medical service`, identifying exactly what must be confirmed
- Use `TBD` for expected due dates and `N/A` where a script-owned field does not apply

## Hospital Billing Rules and Charge Logic (13:30–13:55 - 25 min)
### Length of stay and charges
- Standard inpatient logic changes to **three midnights and four days**
- Standard bill-hold duration changes from four days to **one day**
- Inpatient and observation encounters use **five ancillary charges per midnight plus one KMA on the final/discharge day**
- Outpatient encounters use the five ancillary charges for the one-day encounter
- Charge totals must explicitly reflect the number of midnights plus the final-day charge
- The CDM value **42163220** was identified for the applicable charge example
- The team corrected terminology around assignment at the **RPBP** level

### PSO and service transitions
- Add a PSO order before charges for inpatient and observation scenarios where the patient transitions appropriately, such as ED to inpatient or ED to observation
- PSO logic should cover applicable status or service changes, including upgrades, downgrades, and transfers between hospital service lines
- Do not add PSO steps to outpatient scenarios by default unless the workflow explicitly requires them
- Exact location, bed, and Cerner/Envision crosswalk requirements remain partly unresolved

### Dummy charges
- Remove zero-dollar accommodation or dummy charges from standard workflows
- Retain dummy-charge logic only for workflows clearly identified as **IME/GME**
- Update the prompt globally so non-IME/GME scripts do not create or reference $0 accommodation charges

## Off-Page Logic and Subject-Matter-Expert Review (13:51–14:18 - 27 min)
### Workflow completeness
- PDF and Visio workflows often provide only approximately **60%** of the end-to-end process because routing, handoffs, inbound messages, SBO activity, and other implied steps occur outside the visible workflow
- A denial workflow may begin with a remittance and routing activity before reaching the displayed workflow
- Medicare secondary billing may require SBO processing, return from SBO, claim completion, balance transfer, and secondary billing steps not represented in the source workflow
- Prompt generation should identify off-page references early and request missing details before producing the full script
- Subject matter experts need to review workflows earlier to identify implied actions, codes, work lists, and handoffs

### Source consistency
- The generated script should not silently diverge from the approved workflow
- Where the source itself appears incomplete or incorrect, the issue should be identified for SME or workflow correction rather than hidden in the generated output
- The team will preserve a copy of each reviewed workbook and compare future iterations against the approved desired output

## Testing Iterations and Reporting (13:58–14:12 - 14 min)
### Failure handling
- The team is considering a test-cycle or iteration field to preserve failure history without duplicating entire scripts
- Testers should resume at the point of failure when the system fix allows it; whether a workflow must restart depends on the failure and workflow dependencies
- PM or project-level tracking may record the number of iterations, while testers primarily need the current executable steps
- A workflow should not reach step N unless the preceding required step has passed, although branching and post-fix restart rules require supervisor or SME confirmation
- Open question: how to retain historical pass/fail results while avoiding multiple copies of the same test script

### Testing scope
- The group questioned whether the current work represents unit testing, system testing, or integration testing
- Unit testing was characterized as more granular, such as verifying whether a single EBU fires correctly
- The current end-to-end scripts appear closer to system or integration testing
